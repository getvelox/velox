# HA readiness — SPOF register and the multi-replica plan (2026-07-06)

> **Amendment 2026-08-30 — the premise below is retired.** The supported
> production posture is now **N ≥ 2 `velox-api` replicas behind a load
> balancer, on managed Postgres with failover + PITR and managed Redis,
> optionally behind a transaction-mode pooler / RDS Proxy.** The trigger
> that gated the multi-replica build ("a design-partner pilot approaching
> production cutover") is treated as fired by decision, not by event;
> every item in the ordered work-item table below is being re-decided under
> that posture in the same session. What this does NOT change yet: the
> code. Until the leader-lease arc (ADR-114, in flight) replaces the
> session-advisory-lock gate, transaction-mode poolers stay unsupported and
> the server still refuses to boot behind them — that refusal is the truth
> of the shipped binary, not of the posture. Single-instance remains a
> supported *deployment size*; it is no longer the design assumption.

> **Design of record for the leader-lease arc: ADR-114 (2026-08-30).**
> Singleton roles (billing, dunning, webhook_outbox, email_outbox,
> webhook_delivery) become tick-scoped rows in `leader_leases`, acquired,
> renewed and released by single self-contained statements on the database
> clock, with a fencing token every leader-only claim statement proves in its
> own snapshot. Consequences for this document: hazards 1, 4, 5, 6 and 11 and
> work items 0, 4, 5, 7 and 8 are re-decided below, in place, each tagged
> `[ADR-114]`. The advisory-lock line-cites in this file describe the binary
> until PR-D of that arc merges; they are history after it.

Single-instance is the supported v1 deployment shape: one `velox-api` process, one Postgres, no load balancer, "~minutes of downtime per deploy/restart is acceptable" ([docs/self-host.md](../self-host.md), Operational posture, lines 55-66). Money paths are crash-safe by construction — invoice generation is idempotency-index exactly-once (internal/subscription/postgres.go:1089-1094), dunning transitions are exactly-once CAS (#325), outbound email/webhooks are durable Postgres outboxes with lease claims, and every scheduler sweep re-derives eligibility from durable state — so process death costs latency, not correctness. What single-instance does NOT give you is redundancy, and what N=2 does not yet give you is safety on a handful of named surfaces. This document is the pre-work for the multi-replica build: every single point of failure, every verified hazard of running two API replicas today, and the ordered work list — so that when a design-partner pilot approaches production cutover (the named trigger, docs/self-host.md:67-69), the build is execution, not discovery. Every claim below carries the file:line it was verified against; surfaces that are already safe say so explicitly.

## SPOF register

Legend: **Lost** = irrecoverable without external action. **Delayed** = self-heals on restart with zero operator work.

### Tier: ingest edge

| Component | Failure | Blast radius | Lost vs delayed | Operator mitigation today |
|---|---|---|---|---|
| Single API process — the only front door for usage. All three ingest doors (`POST /v1/usage-events`, `/batch`, `/v1/integrations/litellm/spend`) are synchronous handlers writing straight to Postgres in-request; no Velox-side queue/WAL/buffer exists (usage/handler.go:146-167; internal/integrations/litellm/handler.go:104-157; internal/usage/postgres.go:110-117) | Process down = connection refused at the edge; Postgres down with process up = failure per-door (see Downtime = money) | Every usage event fired during the window is refused. Nothing already accepted is ever lost — writes are synchronous, so 2xx means committed (usage/postgres.go:110-117) | **Split**: delayed for clients that retry non-2xx; **permanently lost** for clients that don't — including LiteLLM at its defaults (see Downtime = money). Loss is invisible afterward | Graceful shutdown drains in-flight requests 30s (cmd/velox/main.go:294-302) so planned deploys yield clean retriable refusals. Keep deploy windows short, away from tenants' period close; require ingest clients to retry with idempotency keys |

### Tier: scheduler / periodic jobs

| Component | Failure | Blast radius | Lost vs delayed | Operator mitigation today |
|---|---|---|---|---|
| Single in-process scheduler goroutine (cmd/velox/main.go:237-241), 1h prod tick hardcoded — no config knob; 5m only when `Env=="local"` (main.go:156-159). No tick at boot: first fire is one full interval after start (internal/platform/scheduler/runner.go:55-73) | Process down ⇒ no invoice generation, dunning advances, auto-charge retries, tax/clawback re-drives, trial flips, pause resumes, credit expiry, threshold hard-cap invoices | Outage + up to 1h post-restart silence, then batch-rate drain: one 50-sub batch per livemode per hourly tick, no drain loop in `RunCycle` (internal/billing/engine.go:1697-1740; scheduler.go:327-402 pass `s.batch` everywhere) — backlog recovery latency scales linearly | **Delayed only.** Every sweep re-derives from durable state (`next_billing_at` in past, `auto_charge_pending`, `next_action_at`); `billSubscription` loops periods per sub so no period is skipped (engine.go:1742-1759) | Supervise with restart=always. For a known backlog: `POST /v1/billing/run` per tenant fully drains that tenant in one call — `RunCycleForTenant` already has the drain-until-empty loop (engine.go:1626-1695). `/health/ready` tracks scheduler liveness (main.go:196-197) | **[ADR-114]** Boot silence closes: a role whose last tick ended more than one interval ago is due at the first poll (≤ 5 s after boot); the cadence becomes a cluster fact (`leader_leases.last_tick_ended_at`), so N replicas run billing once per interval, not N times.

### Tier: outbound dispatchers (email outbox, webhook outbox, webhook retry)

| Component | Failure | Blast radius | Lost vs delayed | Operator mitigation today |
|---|---|---|---|---|
| All four background workers run only as goroutines inside `cmd/velox` — no separate worker deployable (cmd/velox/main.go:238-284) | Process down halts ALL outbound email (invoices, receipts, dunning, password resets, invites — internal/email/dispatcher.go:160-191) and every outbound webhook | Zero outbound delivery tenant-wide for the outage duration; backlog drains on restart at tick rates (email 5 rows/5s; webhook 25 rows/2s — email/dispatcher.go:79-88, webhook/dispatcher.go:53-58) | **Delayed only.** Queues are durable Postgres tables; rows stay `pending` and are claimed on restart (email/outbox.go:264-268; webhook/outbox.go:179-184; webhook/postgres.go:727-737). One decay case: time-boxed links (1h password-reset tokens) delivered after a >1h outage arrive dead — user re-requests | Process supervision. Monitor PendingCount/FailedCount gauges (email/outbox.go:407-421, 536-550; webhook/outbox.go:326-359). **This tier needs zero code for HA** — a second replica is already safe (see verified-safe) |

### Tier: API state (Redis)

| Component | Failure | Blast radius | Lost vs delayed | Operator mitigation today |
|---|---|---|---|---|
| Redis — in production the general and hosted-invoice rate limiters are **fail-closed** (internal/api/router.go:1087-1089, 1118-1120); nil client or any Redis error ⇒ 429 for every covered request (middleware/ratelimit.go:143-159) | Redis down or `REDIS_URL` unset in prod: operator/dashboard API 429s — login EXCLUDED as of this audit's PR (/v1/auth previously mounted the fail-closed general limiter, contradicting the stated #21 design; it now has its own never-fail-closed instance); hosted invoice pay pages, payment-update links, cost dashboards 429 (router.go:1216, 1240). ### Tier: datastore (Postgres + key material)

| Component | Failure | Blast radius | Lost vs delayed | Operator mitigation today |
|---|---|---|---|---|

## What breaks at N=2 today

Verified hazards only, ordered by severity. Everything not listed here was checked and is in the verified-safe list below.

### Hazards

**1. [SHIPPED 2026-07-06 — per-invoice CAS claim, migration 0141] The auto-charge sweep was the one lock-gated money path with no row claim — a Postgres-failover dual-leader window could double-charge one invoice.** Fix landed as `ClaimAutoCharge` (dunning-shaped CAS re-asserting the full eligibility predicate, 5m lease, DB-side now(), updated_at untouched for idempotency-key stability) at the top of the `processAutoCharge` loop, with release-on-skip for the two provably-pre-Stripe paths. Deliberately NOT claim-in-list: a batch-stamped lease cannot cover a serial 50-invoice loop, and the list methods are shared with dunning enrollment, which a claiming list would starve (adversarial review). Pinned by: real-Postgres claim collision, dual-leader charges-once, predicate-recheck matrix, updated_at-stability, claim-blind lists, release-on-skip tests. Original finding: A failover releases session advisory locks while the old leader's tick keeps running: the lock pins one conn (advisory_lock.go:44-47, 62-79), tick work runs on other pool conns that reconnect to the new primary, the scheduler never rechecks lock liveness mid-tick (scheduler.go:271-282), and `Release()` swallows errors (advisory_lock.go:90). During the overlap, every duplicated step collapses via SKIP LOCKED / CAS / idempotency-index — except the auto-charge sweep: `ListAutoChargePending` is a plain SELECT with no claim (invoice/postgres.go:1813-1827), and its only dedupe is the Stripe idempotency key derived from `inv.UpdatedAt` (payment/stripe.go:451-484). The divergent-key path: leader A's charge outcome persists as failed/unknown via `UpdatePayment` (bumps `updated_at`, status stays finalized, invoice/postgres.go:703-709); leader B's refresh (engine.go:5339-5344) then mints a NEW key — `chargeInvoice` checks only Status and amount_due, never payment_status (stripe.go:409-426). Double charge fires when A's outcome was UNKNOWN but the PI actually succeeded. Rare (failover coinciding with a tick), customer-visible, refundable, never silent (both PIs emit webhooks). Fix: give the sweep the dunning-shaped CAS claim (a bare `FOR UPDATE SKIP LOCKED` is insufficient — the list tx ends before the charge loop). *[ADR-114] The mechanism behind the original finding — a session lock pinned to one connection while the tick ran on others — no longer exists; leadership is a row, and a Postgres failover leaves exactly one token valid. The per-invoice CAS claim stays as the money guarantee.*

**2. Rolling-deploy binary skew permanently DLQs money emails of a new `email_type`.** *[SHIPPED 2026-08-30 — unknown `email_type` is `ErrUnknownEmailType`, retryable and attempt-capped; a newer replica delivers it, a type no binary knows still DLQs at the cap.]* `email_outbox.email_type` deliberately has no CHECK constraint (outbox_sender.go:40-43, exercised by ADR-082's `TypeCreditNote`), the old binary's dispatcher returns `ErrPayloadDecode` for unknown types (dispatcher.go:189-190), which is classified permanent (outbox.go:81-87) and DLQ'd with zero retries (outbox.go:338-343). The per-tick dispatcher lock is won arbitrarily by either binary (dispatcher.go:118-127), so new-type rows claimed by the OLD binary in the overlap window are dead — not delayed. A per-row `slog.Error` fires (outbox.go:344-351) but `FailedCount` has zero callers and no redrive tooling exists (verified by grep); recovery is hand-written SQL. Inert at N=1. Fix (shipped): unknown type ⇒ retryable backoff.

**3. [AMENDED 2026-08-30 — the `migrate.go` comment clause below was fixed by #395 on 2026-07-06 (the code now WARNs and continues and says so honestly); the expand/contract discipline, the DDL lint and ADR-116/117 remain open as program Phase 3] Old-code-on-new-schema windows are governed by nothing.** When `dbVer > embedded`, `CheckSchemaReady` WARNs and returns nil while its own inline comment says it should refuse (migrate.go:1075-1090; the exported godoc at 1045-1055 promises nothing either way). Leader election is version-blind — fixed lock constants, no version affinity (main.go:193) — so during a rolling deploy the OLD replica's scheduler/dispatchers can keep winning the locks and run old billing/dunning code against the new schema for the whole window (unbounded if the rollout wedges at 1-old/1-new). No expand/contract migration discipline exists; `cmd/velox-migrate-safety` measures lock holds and duration, not old-binary compatibility (its main.go:1-37). Worst case is silent data mis-writes, not downtime. Fix: decide + document the skew contract, fix the comment, optionally lint destructive DDL.

**4. [AMENDED 2026-08-30 — ADR-114: the lock below is now a lease the wedged tick keeps renewing (its heartbeat goroutine is alive even when the work is stuck), so the effect is unchanged: the role stays held; `velox_leader_last_tick_age_seconds` growing while `velox_leader_held` stays 1 is the cluster-wide signal this hazard lacked] Health model masks a wedged scheduler leader at N=2.** Ticks have no per-tick timeout (runner.go:55-90) and each advisory lock lives on a dedicated conn released only by `Release()` or session drop (advisory_lock.go:62-92) — a tick wedged mid-half holds that half's lock indefinitely. The wedged pod's `/health/ready` goes 503 (LB pulls it) but K8s liveness `/health` is an unconditional 200 (router.go:1172-1173, 1447-1449), so nothing restarts it; followers report ready because `onRun` fires on lock-skipped ticks (scheduler.go:249-254). Billing and dunning are separate lock keys (scheduler.go:271-282 vs 485-496), so exactly ONE half stops cluster-wide; the per-pod staleness metric still fires for the pulled pod (runbook.md:32) — alertable, not silent, but only if metrics alerting is deployed. Related N=1 hazard: readiness couples traffic to scheduler pace — a steady-state tick gap >2× interval 503s the sole replica's readiness and self-inflicts a full API outage (router.go:1474-1481; runbook.md:11-12 wires it as the LB check). A restart's long first tick does NOT trigger it (zero lastRun ⇒ "ok: awaiting first run", router.go:1482-1483). Fix: per-half tick timeout; decouple readiness from scheduler staleness; make scheduler liveness a cluster fact persisted in the DB. *[ADR-114] Cluster-visible half shipped by the arc: `leader_status` + `velox_leader_last_tick_age_seconds{role}`. The per-role tick deadline and the readiness swap remain open (work item 5).*

**5. [CLOSED 2026-08-30 — ADR-114 fence (cutover PR-D) + the two CAS fixes shipped in PR-B (`ClearPauseCollection` CAS, watermark CAS); the effect-firer audit is recorded as ADR-114's first amendment: every effect reachable from a leader tick sits behind a conditional write] Advisory-lock leadership has no fencing: dual-leader overlap duplicates non-CAS side effects (outbound webhook events).** Same failover mechanism as hazard 1; money converges everywhere, but effect-firing tied to idempotent-but-not-CAS writes duplicates — e.g. pause auto-resume: the SKIP LOCKED list tx rolls back before the clear (subscription/postgres.go:1211-1252), `ClearPauseCollection` is unconditionally idempotent with no changed-rows signal (postgres.go:643-679), and each overlapping tick fires `subscription.collection_resumed` via a fresh outbox enqueue (service.go:2337-2358; outbox.go:97-117). The duplicates carry DIFFERENT envelope ids (separate `Enqueue` calls, distinct timestamps), so the documented dedupe-on-event-id guidance (docs/webhooks.md:126) does NOT collapse them — consumers see true semantic duplicates. Rare window; fix is a cheap lock-liveness probe (`SELECT 1` on the lock conn between phases, abort tick on error) rather than full fencing tokens. *[ADR-114] A leader that has been superseded, expired or paused admits zero rows from the first claim statement that starts after the change committed (`leader_fence()` in the five claim funnels), and its work ctx is cancelled within one heartbeat. The one named non-CAS effect-firer (`ClearPauseCollection` → `subscription.collection_resumed`) becomes a CAS. Residual: outbound events remain at-least-once across a takeover — a frozen process that resumes may complete one already-started statement.*

**6. [MOOT 2026-08-30 — ADR-114 deletes `VerifyAdvisoryLockTopology` in PR-D] Topology self-check has a contention false-pass under restart loops.** `VerifyAdvisoryLockTopology` returns nil when its probe lock is already held, assuming a concurrent booter ("its passing verdict covers this topology too", advisory_lock.go:139-143). Behind a transaction-mode pooler, a first boot that acquires the probe lock and then fails a later probe strands it (the PID-flip path at :145-150 errors without unlocking); every subsequent boot inside the strand window (systemd restart loop, second replica) sees `got=false` ⇒ nil ⇒ starts behind the forbidden pooler, where all five worker locks then strand silently — the exact "week of missing invoices with zero errors" the check exists to prevent (main.go:144-148). Window is minutes-to-an-hour per strand on stock PgBouncer timeouts, but restart loops retry in seconds and the effect persists as long as the topology does. Fix: retry acquisition 3×200ms and fail boot if still contended (~10 lines).

**7. **11. [SHIPPED 2026-07-06 — ClaimChargeForDunningRetry, same lease column] Sweep vs dunning retry could double-charge via purpose-suffixed idempotency keys.** Fix: the dunning retry path takes the shared per-invoice lease before charging (predicate `payment_status IN ('pending','failed')` — 'unknown' deliberately excluded so ambiguous outcomes wait for the reconciler, which also closes the same-tick N=1 window: the billing half's unknown outcome followed seconds later by the dunning half's due retry); claim-lose maps to ErrTransientSkip (no attempt burn). ### Verified safe at N=2 — do not re-flag

- **Ingest dedup**: fully DB-level — `ON CONFLICT (tenant_id, livemode, idempotency_key) DO NOTHING`; both doors translate the loser to success (usage/postgres.go:113-115, 169, 182-186; usage/handler.go:171-187; litellm/handler.go:183-197). Batch is one all-or-nothing tx (usage/postgres.go:44-78).
- **Rate limiting with healthy Redis**: shared GCRA buckets, per-limiter namespaces — global limits, no per-replica doubling (ratelimit.go:19-37, 171-208; router.go:1077-1128).
- **API Idempotency-Key middleware**: Postgres-backed reserve-before-act; racing replicas resolve one winner, the loser polls the DB for the winner's response; DB-error fail direction is 409-retry, never re-execute (middleware/idempotency.go:102-131, 203-234, 298-323).
- **Dashboard sessions**: fully DB-backed incl. cross-replica revocation; nothing session-shaped in process memory (session/store.go:42-136).
- **Scheduler lock coverage is COMPLETE**: every scheduler job — 7 reconcilers, auto-charge retry, dunning enrollment, threshold scan, trial expiry, pause resume, RunCycle, credit expiry, cross-mode cleanup — runs inside exactly one of the two advisory-lock scopes (scheduler.go:268-299, 480-508; main.go:193). Followers stay health-green (onRun fires on skipped ticks, scheduler.go:249-254).
- **Invoice generation is exactly-once independent of the leader lock**: `idx_invoices_billing_idempotency`, loser gets 23505 and skips gracefully (subscription/postgres.go:1089-1094).
- **Trial expiry / pause resume double-processing**: SKIP LOCKED candidate fetch with explicit multi-replica rationale + CAS status flips (subscription/postgres.go:2004-2008, 2067-2090, 735/832/886). Credit expiry converges (`ExpireGrantAtomic`, credit/service.go:469-500).
- **All three drainers (email outbox, webhook outbox, webhook retry)** *(amended 2026-08-30: the two tests named below cover the email outbox and the webhook RETRY claim; the webhook-OUTBOX drainer's own claim was held by convention until `TestOutbox_ProcessBatch_SkipsRowsLockedBySibling` (pins `FOR UPDATE SKIP LOCKED`) and `TestOutbox_ProcessBatch_ConcurrentClaimersDisjoint` (pins the claim lease) — each mutation-verified to go red for exactly its own mechanism.)*: two-layer design — per-tick advisory-lock gating for efficiency, claim-lease + `FOR UPDATE SKIP LOCKED` + CAS status marks for correctness, disjointness pinned by tests (`TestP5_ConcurrentClaimersDisjoint`, `TestListPendingDeliveries_ConcurrentClaimersDisjoint`). ## Downtime = money?

The honest answer: **inside Velox, nothing is ever lost — the entire loss surface is the ingest edge, and it is decided by client retry behavior.** Writes are synchronous, so 2xx means committed; everything pending (billing cycles, dunning steps, auto-charges, outbox rows) is durable and self-heals on restart (docs/ops/backup-considerations.md documents the full resume ledger with validation queries). Inbound Stripe webhooks 5xx during an outage and Stripe retries for ~days, with the payment_unknown reconciler as backstop. What does NOT self-heal:

**1. LiteLLM usage fired while Velox is down is permanently lost at LiteLLM's defaults — this was an open question and is now source-verified (BerriAI/litellm main, read 2026-07-06).** LiteLLM's `generic_api` logger defaults `max_retries=0` and its `async_send_batch` ends with `finally: self.log_queue.clear()` — on ANY send exception the batch is dropped, no re-queue, no durable buffer. Consequences: (a) the repo's three claims that "LiteLLM retries (only) on 5xx" (docs/adr/033-litellm-spend-adapter.md; router.go:1093-1096; litellm/handler.go:104-107) are **false at current LiteLLM defaults** — 5xx raises via `raise_for_status()` into the same drop path, so Postgres-down loses events exactly like process-down; (b) retries are operator-configurable (`max_retries`/`retry_delay`), which shrinks but never closes the window; (c) a LiteLLM-proxy restart loses its in-memory `log_queue` even while Velox is healthy. Two Velox-side aggravators verified in-repo: during a full Postgres outage the request dies at API-key auth, which masks DB failure as **401** (auth/middleware.go:37-47, ADR-026 anti-enumeration) — not a retryable status under any config; and on partial DB failure the spend handler appends persist errors to the envelope and returns **200 OK** unconditionally (litellm/handler.go:138-143, 156) — the comments claiming storage errors propagate as 5xx describe code that does not exist. At the rate-limit sizing floor (>1.7 calls/s, router.go:1094), a 2-minute deploy is ~200+ silently unbilled calls.

**2. The recovery path exists and is clean — but has a hard deadline.** Deterministic per-call idempotency keys (`<litellm_id>:input/:cache_read/:output`, mapper.go:220-243), DB-level `ON CONFLICT DO NOTHING`, and silent-success replay make operator re-POST of LiteLLM's own spend logs a pure gap-filling replay with preserved original timestamps (mapper.go:139-148). The deadline: by documented design (usage/service.go:214-226, "KNOWN BEHAVIOR"), an event whose timestamp falls in an already-finalized period is stored but **effectively unbilled** — aggregation is strictly timestamp-windowed (usage/postgres.go:344-393) and nothing true-ups closed periods. Replay after finalize preserves the audit ledger but not the revenue; recovery then means a manual invoice adjustment. A downtime window straddling period close, discovered late, is the permanent-loss case. The late-event counter named in that comment is the smallest visibility fix.

**3. Direct API clients**: delayed if they retry non-2xx, lost if they don't. The retry contract ("non-2xx means not recorded — retry; replays are dedup-safe") is not yet stated in the ingest docs. One narrow pre-existing N=1 hazard, N=2-neutral: a **keyless** single-event POST whose response died to a hard crash (kill -9 between commit and response; graceful deploys drain 30s) double-bills on retry — keyless events have "no dedup line of defense" (usage/postgres.go:48), NULLs never conflict. Batch is immune even keyless (one tx); LiteLLM is immune (always keyed). Docs-first fix; do not reject keyless (Stripe meter events accept keyless too).

**4. Shutdown mechanics** *(SHIPPED 2026-08-30 — three-stage 90s budget: HTTP 30s → catch-up 30s → workers 30s; readiness-first drain with `SHUTDOWN_DRAIN_DELAY`; SSE subscribers closed on shutdown; compose grace 120s. The paragraph below is the pre-fix analysis.)*: worst-case drain is ~11min (HTTP 30s → test-clock catchup up to 10min on a `context.Background()` ctx that shutdown cannot cut short, catchup.go:57/147, main.go:294-328 — the comment at main.go:308-309 claiming otherwise is wrong → workers 30s), exceeding K8s' default 30s grace; SIGKILL mid-anything is designed-for (outbox rows pending, catchup resumes at boot). Set grace ≥ ~75s and cap the shutdown catchup wait. Unclean kills also cost bounded at-least-once duplicates: ≤5 emails + ≤10 webhook POSTs re-sent once each, webhooks with the SAME event id (receivers dedupe; SMTP can't), and one of 15 attempts burned per claimed in-flight row — deliberate, so a crash-looping row still converges to the DLQ (email/outbox.go:189-196; webhook/postgres.go:436-446).

**5. Restore-to-earlier-point and key loss** (see SPOF register): duplicate outbox re-fires + lost open-period usage unless PITR; a DB backup without `VELOX_ENCRYPTION_KEY` is unrecoverable.
